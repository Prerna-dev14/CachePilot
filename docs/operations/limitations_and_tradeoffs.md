# CachePilot Operational Trade-Offs, Failure Modes & System Limitations

## 1. Executive Summary
CachePilot is engineered to maximize cost efficiency and minimize query latency in enterprise Retrieval-Augmented Generation (RAG) systems without compromising tenant isolation, data freshness, or answer correctness. Operating this architecture involves deliberate trade-offs across semantic precision, cache invalidation, financial modeling, and model routing.

---

## 2. Semantic Similarity Threshold Trade-Offs ($\tau = 0.88$)

### The Trade-off
- **Conservative Default ($\tau = 0.88$)**: Ensures that cached answers are only reused when a candidate query exhibits overwhelming semantic equivalence. Minimizes false-positive cache hits where subtle nuance differences (e.g., negative polarity, different sub-clauses) would otherwise yield incorrect answers.
- **Lower Threshold ($\tau \in [0.75, 0.84]$)**: Significantly increases the cache hit rate (by up to 25–40%), but introduces the unacceptable risk of answering a subtly different question with outdated or incorrect context.
- **Higher Threshold ($\tau \in [0.93, 1.00]$)**: Collapses semantic caching into near-exact lexical matching, rendering Tier-2 vector similarity search redundant.

### Recommendation
Retain the default conservative threshold ($\tau = 0.88$) for legal, financial, and clinical corpora. Lowering $\tau$ below $0.85$ requires continuous regression testing against the offline evaluation benchmark suite.

## 3. Financial Telemetry & Non-Authoritative Billing Disclosures

### Non-Authoritative Policy (`is_authoritative_billing: false`)
Every query response, ledger record, and dashboard metric generated by CachePilot includes an explicit flag: `is_authoritative_billing: false`.

### Operational Rationale
1. **Model Provider Pricing Complexity**: Upstream providers (OpenAI, Anthropic, Bedrock) employ dynamic pricing structures, volume discounts, regional tariffs, and prompt caching discounts that cannot be authoritatively mirrored in real-time.
2. **Token Counter Variance**: Heuristic and BPE token estimators (e.g., TikToken) may diverge by 1–3% from upstream provider invoice counts.
3. **Audit Compliance**: Financial systems require immutable invoices generated directly by cloud billing providers. CachePilot's telemetry serves as an operational estimator for routing decisions, cost attribution, and budget alerts—not customer-facing invoices.

## 4. Dual-Tier Cache Consistency & Invalidation Latency

### Architecture
- **Tier 1 (Exact Match)**: Sub-millisecond lookup in Redis (or in-memory fallback) using SHA-256 deterministic key formula.
- **Tier 2 (Semantic Cosine Search)**: 3–8ms vector similarity search in PostgreSQL with pgvector HNSW indexing, partitioned strictly by `tenant_id` and `security_scope`.

### Consistency Model & Limitations
- **Corpus Versioning (`corpus_version`)**: Ingesting or updating documents increments the active corpus version. This immediately invalidates previous cache entries for that scope without requiring mass database deletes.
- **Cache Purge Latency**: In multi-replica distributed deployments, Redis cluster replication and pgvector index updates exhibit eventual consistency (typically < 100ms). During a high-throughput update window, a brief cache lookup window exists where older entries might be served until the key expires or TTL elapses.
- **TTL Bounds**: Default cache entry TTL is set to 24 hours (`86400s`), with configurable minimums.

## 5. Model Routing Policies & Fallback Latency Penalties

### Small vs. Large Tier Economics
- **Small Model (`mock-fast-small`)**: $0.0000005/token input, $0.0000015/token output. Average latency: ~12–15ms.
- **Large Model (`mock-reasoning-large`)**: $0.0000050/token input, $0.0000150/token output. Average latency: ~30–45ms.
- **Routing Savings**: Routing simple factual lookups to the small model produces an ~90% cost reduction and ~60% latency reduction on those queries.

### Fallback Penalty
If the small model fails (timeout, upstream 5xx, or provider outage), the `RouterService` executes an automated fallback to the large model with reason code `FALLBACK_RETRY`.
- **Latency Impact**: Total latency becomes $(latency_{small\_attempt} + latency_{large\_retry})$.
- **Design Decision**: Prioritize system availability and answer correctness over strict latency bounds when an upstream model fails.

## 6. Security Boundaries & Rate Limiting

### Multi-Tenant Hard Boundaries
- **Zero Cross-Tenant Retrieval**: Every vector search and cache key includes hard tenant partitions (`WHERE tenant_id = :tenant_id AND security_scope = :security_scope`).
- **Cryptographic Cache Keys**: Key collisions across scopes with ambiguous delimiters (e.g., `tenant:admin` vs `tenant_admin`) are mathematically eliminated via fixed-delimiter canonical tuple hashing.

### Client Rate Limiting
- **Default Limit**: 120 requests per minute per client IP or `X-API-Key`.
- **Exemptions**: `/health/live` and `/health/ready` probe endpoints are exempt to prevent cascading Kubernetes readiness flaps.
- **Threshold Response**: Returns HTTP 429 Too Many Requests with standardized `Retry-After: 60` and `X-RateLimit-Limit` headers.
